# Source and code identity

A source file's bytes, an executed script or native image, and their mapping are separate evidence. Hunin records their identifiers and the basis of each association. A matching file name does not establish a build relationship.

For Node, the collector observes `Debugger.scriptParsed` and retrieves that isolate's script text through Inspector. It retains the generated code, its SHA-256, the linked source-map bytes and their SHA-256, and available original source content. Regular and indexed maps are decoded. Profile frames match by process, thread/isolate, script ID and script URL; their `code_id` identifies the observed generated script. Mapped frames retain their generated coordinates in `attributes.script_sources`.

This is a runtime-linked map, not a proof that a compiler emitted correct mappings. Embedded `sourcesContent` is retained directly. When a map omits it, separately captured project files have the weaker `filesystem_at_script_parse` basis. A conflicting script digest, map URI/file field, embedded original content, debug ID or isolate namespace prevents mapping. Multiple observed code versions with the same isolate script ID remain ambiguous. Missing originals keep generated positions. The importer never fetches a missing map or original from the network.

Bun and Deno report their own profile positions. Hunin preserves these positions rather than mapping them a second time. Deno can also retain Inspector-observed generated code; reading its original TypeScript remains subject to the target's existing read permissions. Bun's local Node Inspector bridge does not emit the required script-parsed events, so captured original files have the explicit `filesystem_at_profile_flush` basis and a scoped runtime script identity. Their original-file contents are not verified against compiled code. These runtime-specific bases remain visible in source provenance.

JavaScript capture is bounded to 2 MiB per source, 8 MiB per map, and 32 MiB per isolate sidecar. Inspector Debugger adds measurement overhead on Node and Deno. An unavailable or denied capture leaves profile observations usable without inventing source evidence. Node workers have distinct source sidecars; a main-isolate script ID is never used as a worker mapping.

Native normalization compares available image bytes with reported Mach-O UUIDs, ELF GNU build IDs, or PE image/CodeView identifiers. An identifier conflict leaves function and source positions unresolved while preserving the profile-reported module, code ID and relative address. This catches an observed samply 0.13.1 address-reuse case where a newly loaded library inherited the previous library's reported identifier. Its raw capture and measured images are retained in the regression fixtures.

Native image snapshots are bounded to 128 MiB each and 256 MiB per profile. The retained image context binds their digests to the original raw profile bytes. Reanalysis verifies those immutable blobs and identifiers; missing, corrupted or unrelated context cannot fall back to current target binaries. Missing image identifiers remain unverified. Identifier agreement alone does not establish a module load instance, load/unload times, or a relationship between debug-file source paths and particular source contents. The current Firefox/samply summary cannot reconstruct missing loader events.

Source snapshots retain the exact URI, contents, digest and code provenance. When one URI has multiple code/content versions, source selection must specify the frame's `code_id`; it must not silently choose the latest version. Generated and original bytes remain available after target files are edited or deleted. V8 call-frame positions commonly identify the function declaration, not an exact instruction executed by each sample; sample weights still describe sampling evidence.
