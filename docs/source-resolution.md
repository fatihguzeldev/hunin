# Source and code identity

A source file's bytes, an executed script or native image, and their mapping are separate evidence. Hunin records their identifiers and the basis of each association. A matching file name does not establish a build relationship.

For Node, the collector observes `Debugger.scriptParsed` and retrieves that isolate's script text through Inspector. It retains the generated code, its SHA-256, the linked source-map bytes and their SHA-256, and available original source content. Regular and indexed maps are decoded. Profile frames match by process, thread/isolate, script ID and script URL; their `code_id` identifies the observed generated script. Mapped frames retain their generated coordinates in `attributes.script_sources`.

This is a runtime-linked map, not a proof that a compiler emitted correct mappings. Embedded `sourcesContent` is retained directly. When a map omits it, separately captured project files have the weaker `filesystem_at_script_parse` basis. A conflicting script digest, map URI/file field, embedded original content, debug ID or isolate namespace prevents mapping. Multiple observed code versions with the same isolate script ID remain ambiguous. Missing originals keep generated positions. The importer never fetches a missing map or original from the network.

Bun and Deno report their own profile positions. Hunin preserves these positions rather than mapping them a second time. Deno can also retain Inspector-observed generated code; reading its original TypeScript remains subject to the target's existing read permissions. Bun's local Node Inspector bridge does not emit the required script-parsed events, so captured original files have the explicit `filesystem_at_profile_flush` basis and a scoped runtime script identity. Their original-file contents are not verified against compiled code. These runtime-specific bases remain visible in source provenance.

JavaScript capture is bounded to 2 MiB per source, 8 MiB per map, and 32 MiB per isolate sidecar. Inspector Debugger adds measurement overhead on Node and Deno. An unavailable or denied capture leaves profile observations usable without inventing source evidence. Node workers have distinct source sidecars; a main-isolate script ID is never used as a worker mapping.

Native normalization compares available image bytes with reported Mach-O UUIDs, ELF GNU build IDs, or PE image/CodeView identifiers. An identifier conflict leaves function and source positions unresolved while preserving the profile-reported module, code ID and relative address. This catches an observed samply 0.13.1 address-reuse case where a newly loaded library inherited the previous library's reported identifier. Its raw capture and measured images are retained in the regression fixtures.

For a PE image without CodeView/PDB information, the pinned collector and symbol reader use the same synthetic debug identifier derived from the first page of `.text`. This keeps symbol selection consistent; it is not a cryptographic build identifier. The generic PE symbol reader also accepts embedded GNU-style `.zdebug_*` DWARF sections, with a 128 MiB decompressed limit per section and checks for truncated, corrupt or size-mismatched data. Available DWARF can supply function/source positions without a PDB. This does not establish a relationship between a debug-file source path and the current contents of that path.

Windows ETW user stacks are associated with CPU samples only by an exact process, thread and original sample timestamp match. Delayed delivery is valid when the StackWalk event's original timestamp matches the sample; a later sample's stack cannot supply callers for an earlier sample. When no matching user stack is available, the sample retains its original SampleProf instruction pointer; that address can still resolve to a function or source position while the caller chain remains explicitly unavailable. Stack availability and module lifetime evidence are independent: a known loaded image does not prove that its sample has a captured caller chain, and a missing chain does not erase the observed instruction pointer or loader evidence.

Sample attributes expose `sample_stack_basis`, `user_stack_available` and `caller_stack_available`. The `sampled_instruction_pointer_only` basis sets both availability flags to false and retains `original_sample_timestamp` as a precision-safe raw counter string and `sampled_instruction_pointer` as a hexadecimal address. Missing or ambiguous exact metadata has an `unavailable` or `ambiguous` basis and null availability flags. A matched one-frame user stack still has no captured callers.

Older Windows processed profiles without per-sample association metadata retain their reported stacks with a diagnostic that the caller chains remain unverified. Reanalysis cannot reconstruct discarded instruction pointers or ETL events absent from the retained inputs.

Native image snapshots are bounded to 128 MiB each and 256 MiB per profile. The retained image context binds their digests to the original raw profile bytes. Reanalysis verifies those immutable blobs and identifiers; missing, corrupted or unrelated context cannot fall back to current target binaries. Missing image identifiers remain unverified. Identifier agreement alone does not establish a module load instance, load/unload times, or a relationship between debug-file source paths and particular source contents. The current Firefox/samply summary cannot reconstruct missing loader events.

Hunin's pinned Samply extension retains a separate lifetime sidecar before absolute stack addresses are converted. The sidecar binds its collector provenance and mapping operations to the exact raw-profile digest. Normalization exposes `module.observed_lifetime` scopes and `sampled_in_code_instance` relations, including distinct loads of the same image at a reused address. Moves and replacements create separate address generations. Within the collector's clock, each generation covers a half-open interval `[start, end)`, so a sample at the replacement boundary selects the new generation. A repeated numeric process or thread ID alone does not establish the same lifetime. macOS dyld snapshots and Linux executable-map snapshots carry observation windows; changes entirely between snapshots remain unobserved. Windows load/unload events retain their event basis, while rundown and missing ends remain censored. Lost events, unavailable snapshots and bounded-output truncation mark the evidence incomplete. Processed profiles without this sidecar retain collector-reported thread scopes and cannot establish module lifetimes.

Source snapshots retain the exact URI, contents, digest and code provenance. `source.read` consults accepted retained snapshots before a live-filesystem fallback. When one URI has multiple code/content versions, pass the frame's `code_id`; Hunin does not silently choose the latest version. Captured generated and original bytes remain available after target files are edited or deleted, within the stated capture and retention limits. Pre-launch project snapshots establish retained file identity, while their relationship to executed native code remains unverified. V8 call-frame positions commonly identify the function declaration, not an exact instruction executed by each sample; sample weights still describe sampling evidence.

`recordings.reanalyze` uses the managed raw artifact and its retained input manifest. Native image-context mode verifies the stored image digests and does not substitute current target binaries. When inspecting inputs through `artifacts.list`, follow `next_cursor` until it is null; the default page contains at most 100 entries, with a maximum requested `limit` of 500. The first page is not a completeness check for a recording.
